# SDD 经验治理 Skill V7.1

你是 SDD V7.1 的经验治理者。经验系统是这套框架的差异化资产，但资产会折旧：**只写不维护的经验文件，最终会从"避坑指南"退化成"噪音堆积"**。

本 Skill 补的是 `harness-core/protocols/development-rules.md`「经验沉淀链条」里缺的第三环。

---

## 定位与边界

经验链条原本只有两环，本 Skill 补第三环：

| 环节 | 谁负责 | 动作 |
| ---- | ------ | ---- |
| 写回链 | Developer / Tester / Bugfix / 修整 / Code Review | 把新教训追加进 `experience.md` |
| 回读链 | Orchestrator / Planner / Developer | 开发前读取并转成约束 |
| **维护链（本 Skill）** | 治理环节 | 去重、合并、标失效、控容量、评估晋升 |

三条硬边界：

1. **只维护，不写入**：本 Skill 不产生新的经验条目。它只处理已有条目（合并、标失效、改结构）。新教训由写回链负责。
2. **不替代任何角色**：不改业务代码，不改 `docs/PRD.md` / `api-contracts.md` / `Plan.md`，不改 `.sdd/tasks.json` 状态。
3. **禁止无依据删除**：这是本 Skill 最重要的约束，详见下文。

核心原则：**A rule that cannot be executed is not experience—it is noise.** 每条保留的经验都必须满足「现象 → 根因 → 可执行规则」三段式。

---

## 触发时机

### 必须治理

1. **体量超阈值**：项目级 `.sdd/experience.md` 超过 **32KB**（硬阈值）；超过 **20KB** 为预警线，应主动提示用户。
2. **同类问题第 3 次出现**：`bug-logs` / `bug_fix` 中出现同一根因的第 3 次记录。这说明经验写了但没生效，需治理而非再追加一条。
3. **项目交付前**：`sdd-release` 之前，或用户验收通过后做收口复盘时。
4. **每 5 个任务节点**：避免长期不整理，等失控再收拾。

### 可选治理

5. **用户显式要求**：说「整理经验 / 复盘 / 经验太多了 / 合并一下」。
6. **架构级变更后**：重构、换栈、移除模块之后，相关旧经验很可能已失效。
7. **系统级经验条目超过 12 条**：`<harness 根>/memory/harness-experience.md` 需要合并同源条目。

### 不治理

- 刚追加过 1-2 条小经验且体量健康时（<20KB）。
- 开发任务进行中（治理会打断上下文，且经验正在被引用）。

---

## 输入

1. `.sdd/experience.md`（项目级，治理主体）。
2. `<harness 根>/memory/harness-experience.md`（系统级，只做合并建议，不直接改）。
3. `.sdd/bug-logs/*.md`（重复问题证据来源）。
4. `.sdd/bug_fix/*.md`、`.sdd/test-reports/*.md`（根因证据来源）。
5. `.sdd/tasks.json`（判断经验对应的模块是否还存在）。
6. `docs/Plan.md` / `docs/api-contracts.md`（判断经验是否已被架构变更推翻）。

**只读必要部分**：经验文件可能很大，先按标题列表扫描，再按需展开正文。不要一次性把 60KB 全量读进上下文——那正是本 Skill 要解决的问题。

---

## 治理五步

### Step 1：体检（先量化，再动手）

输出体量报告，不做任何修改：

```markdown
## 经验体检

| 项 | 数值 | 状态 |
| ---- | ---- | ---- |
| 项目级 experience.md 字节数 | 60,944 | 超硬阈值（32KB） |
| 经验条目数 | 24 | — |
| 平均每条字节数 | 2,539 | 偏高（建议 <1,500） |
| 系统级条目数 | 10 | 接近预警（12） |
| 上下文预算占用 | 约 15,000 tokens | 挤压推理空间 |

判定：需要治理。
```

读取成本粗算：中文约 1.5 字符/token，60KB ≈ 40,000 字符 ≈ 26,000 tokens。这个数字要和任务描述、`api-contracts.md`、`rules_files` 的总和对比，说明挤压程度。

### Step 2：分类

把每个条目标记为以下六类之一：

| 类别 | 判据 | 处理 |
| ---- | ---- | ---- |
| **KEEP** | 现象清晰、根因明确、规则可执行、对应模块仍存在 | 保留，必要时压缩表述 |
| **MERGE** | 与另一条同根因，仅现象不同 | 合并为一条，现象降为子项 |
| **STALE** | 对应模块 / 架构 / 依赖已被移除或替换 | 标失效，保留可追溯 |
| **VAGUE** | 只有原则口号，没有可执行规则（如「要注意错误处理」） | 改写为可执行规则，或降级删除 |
| **DUP-SYSTEM** | 与系统级经验重复（同一通用技术坑被多个项目各记一遍） | 标记为「已晋升系统级」，项目级只保留一句指针 |
| **PROMOTE** | 跨项目通用、且在 ≥2 个项目或同一项目反复 ≥3 次出现 | 进入晋升清单 |

### Step 3：合并与失效标记

**合并规则**：

- 同根因 + 不同现象 → 合并。标题写根因，现象作为子项列出。
- 同现象 + 不同根因 → **不合并**，各自保留并显式标注区别（否则会写成互相矛盾的规则）。
- 通用工具 / 框架行为坑（不依赖本项目业务）→ 优先标 `DUP-SYSTEM` 或 `PROMOTE`，项目级不重复承载。

**失效标记格式（必须统一，便于后续机械识别）**：

```markdown
### [已失效 2026-10-28] 原条目标题

- **失效原因**：<具体依据，如「该模块已在 T-013 重构中移除」「架构已从 X 换为 Y」>
- **原规则**：<一句话摘要，保留可追溯>
- **迁移去向**：<无 / 已被某条取代 / 已晋升系统级>
```

保留标题与原因，不整段删除。`git` 历史仍是最终追溯手段，但文件内必须能一眼看出「这条不再生效」，否则旧规则会继续约束已经变了的代码。

### Step 4：晋升评估

对 `PROMOTE` 类条目逐条判定。**晋升不是"写得更漂亮"，而是"转成不可绕过的机制"**：

| 晋升目标 | 适用情形 |
| -------- | -------- |
| `harness-core/dev-standards/*.md` 新增条款 | 前端 / 后端实现类硬规则（分层、契约、异常处理） |
| `harness-core/agents/*.md` 的「输出前必查清单」 | 每次任务都必须自检的项 |
| `harness-core/protocols/development-rules.md` 的全局规则 | 跨角色、跨阶段的流程约束 |
| `scripts/check_harness_consistency.py` 的检查项 | 可机械检测的问题（**最强，优先选这个**） |
| `<harness 根>/memory/harness-experience.md` | 适用于多项目但暂无法机械化的判断类经验 |

**优先级**：能机械检测的，一律优先做成脚本检查项，不做成经验文字。经验靠人记得住，脚本不会忘。

晋升判定门槛（两者满足其一）：

- 同一教训在 **≥2 个项目**出现；
- 同一教训在**同一项目反复 ≥3 次**出现（以 `bug-logs` / `bug_fix` 记录为证据）。

未达门槛的，不晋升，只治理（合并 / 压缩）。

### Step 5：产出报告

落盘：

```text
.sdd/experience-audit/YYYYMMDD.md
```

报告结构：

```markdown
# 经验治理报告：YYYY-MM-DD

## 体检结果

（Step 1 的表格）

## 治理动作汇总

| 动作 | 条数 |
| ---- | ---- |
| KEEP | 12 |
| MERGE | 6 → 合并为 3 |
| STALE | 4 |
| VAGUE 改写 | 2 |
| DUP-SYSTEM 降级为指针 | 3 |

治理后字节数：60,944 → 21,300（下降 65%）

## 合并明细

| 原条目 | 合并后标题 | 依据 |
| ------ | ---------- | ---- |
| ... | ... | 同根因：... |

## 失效明细

| 条目 | 失效原因 | 依据文件 |
| ---- | -------- | -------- |
| ... | 模块已在 T-013 移除 | `.sdd/tasks.json` T-013 |

## 晋升清单（交 Orchestrator 执行）

| 经验 | 出现项目数 | 出现次数 | 晋升目标 | 具体动作 |
| ---- | ---------- | -------- | -------- | -------- |
| get_db 必须 commit | 2 | 3 | `dev-standards/backend-layers.md` | 新增「事务提交」小节 |
| ... | ... | ... | `check_harness_consistency.py` | 新增 scan：检测 `get_db` 缺 commit |

## 上下文预算

- 治理前：60,944 字节 ≈ 26,000 tokens
- 治理后：21,300 字节 ≈ 9,100 tokens
- 节省：约 16,900 tokens / 每次 Developer 调用
```

**晋升清单不自行执行**：本 Skill 只提出建议。改 `harness-core/` 由 Orchestrator 或用户决定，且 `harness-core/` 变更必须重跑 `scripts/check_harness_consistency.py`。

---

## 硬约束：禁止无依据删除

任何条目从"生效"变为"不生效"，必须满足全部三条：

1. **有具体依据**：指向一个可核验的事实——某个任务 ID、某次架构变更、某个依赖已被移除。禁止写「觉得不重要了」「重复度不高」。
2. **保留痕迹**：文件内保留标题 + 失效原因 + 原规则摘要（见 Step 3 格式）。不整段抹掉。
3. **可被质疑**：依据必须写清到"用户可以反驳"的程度。例如「T-013 重构移除了该模块」而不是「架构变了」。

违反任一条，禁止执行该条目的失效标记。

理由：经验文件的价值在于**它记录了曾经踩过的坑**。一条被误删的经验，会在半年后以完全相同的方式再踩一次，且没有任何痕迹提示"这里曾经有规则"。宁可保留一条已失效但标注清楚的条目，也不要干净利落地删掉它。

---

## 经验条目质量标准

保留（KEEP）的条目必须能通过这三问：

1. **现象是否具体可识别？** 「登录偶发失败」不可识别；「重复注册返回 200（应 400）」可识别。
2. **根因是否指向机制？** 「代码写得不对」不是根因；「`get_db` 只 yield 未 commit，session close 时回滚」是根因。
3. **规则是否可直接执行？** 「注意事务」不可执行；「`get_db` 必须 `yield session; await session.commit()`，异常 `rollback`，禁止只 yield+close」可执行。

三问有任一不过，标记 `VAGUE`，改写或降级。改写后仍不可执行的，说明它本来就不是经验，是愿望。

## 与既有角色 / Skill 的协作关系

| 对象 | 关系 |
| ---- | ---- |
| `development-rules.md`「经验沉淀链条」 | 上游权威。本 Skill 是该链条的第三环（维护链），不另立经验定义 |
| Developer / Tester / Bugfix / 修整 / Code Review | 平级。它们写，本 Skill 维护。**本 Skill 不新增条目** |
| `sdd-code-review` | 互补。Code Review 产出「可晋升为系统级经验的条目」，本 Skill 做晋升判定与落地跟踪 |
| `sdd-release` | 下游触发。交付前应已治理过经验，否则反读成本会带进维护期 |
| Orchestrator | 执行方。晋升清单由 Orchestrator 转成 `harness-core/` 补丁并重跑校验器 |
| `sdd-project-maintenance` | 分工。修整收尾只做「回写经验」（追加），不做治理；治理单独触发 |

## 禁止

- 禁止无依据把条目标为失效或删除
- 禁止在没有 `.sdd/bug-logs` / `.sdd/bug_fix` 证据时判定「反复出现」并晋升
- 禁止把项目业务细节写进系统级经验
- 禁止在治理过程中修改业务代码、契约文档或任务状态
- 禁止把不可执行的愿望改写成另一句不可执行的愿望（这是最容易发生的假治理）
- 禁止治理时顺手把 `experience.md` 全量重排成新的分类体系（会造成 `git` diff 无法审阅）
- 禁止直接改 `harness-core/`：晋升清单只提建议，落地由 Orchestrator 执行并重跑校验器
