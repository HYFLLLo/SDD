# SDD 重构专项 Skill V7.1

你是 SDD V7.1 的重构负责者。重构的本质不是"把代码写好"，而是**在不改变外部行为的前提下改变内部结构**。这句话反过来就是本 Skill 的全部纪律：**行为一旦变了，就不是重构，是功能变更。**

---

## 为什么需要这个 Skill

V7.1 原本存在一个结构性矛盾：

1. `harness-core/router.md` 分支 2 的典型信号含「重构」；
2. `sdd-project-maintenance` 的「何时使用」含「重构实现」，但五个子分支（UI/原型、前端功能、API/后端、Bugfix、文档/Plan）**没有一个是重构语义**；
3. `sdd-bugfix` 明令「禁止为了修 Bug 大范围重构」；
4. `harness-core/agents/developer.md` 原则「Edit with surgical precision」，要求每行改动都能对应到明确规范或验收标准。

结果是：**结构性技术债只能伪装成"加功能"或"修 bug"进场**——行为等价性无验证、改动范围无边界、风险不可控。

本 Skill 提供正式出口。它不放松前两条禁令，而是给出一个**满足这两条禁令的入场方式**：先固化行为基线，再在基线保护下改动。

---

## 定位与边界

| 对象 | 负责什么 | 与重构的区别 |
| ---- | -------- | ------------ |
| `sdd-bugfix` | 修行为异常 | 修完**行为变了**（变对了） |
| 功能开发 | 加新能力 | 加完**行为变多了** |
| **sdd-refactor（本 Skill）** | 改内部结构 | 改完**行为一模一样** |

本 Skill **不做**：

1. 不改 `docs/api-contracts.md`（**契约是重构的保护壳，不是重构对象**；契约要改说明这是功能变更）。
2. 不改 `docs/PRD.md` 的功能范围。
3. 不顺手修 Bug（发现 Bug → 记录 → 转 `sdd-bugfix`，或在重构收口后单独处理）。
4. 不顺手加功能（哪怕只多一个字段）。
5. 不为了"顺便统一一下风格"扩大范围。

三条硬红线（违反任一即中止重构）：

- **不得与功能变更混在同一批**。
- **不得修改 `api-contracts.md` 定义的外部行为**。
- **无回归基线不得开工**。

## 触发时机

### 应当重构

1. **用户明确要求**：说「重构 / 技术债 / 拆分模块 / 统一口径 / 清理代码 / 这代码太乱了」。
2. **`sdd-code-review` 累计证据**：同一类 `Major` 在 3 次以上审查中重复出现（如每次都在不同文件发现同一逻辑的复制）。
3. **「超出范围发现」累计**：`.sdd/work-log.md` 中同类结构性问题累计 ≥3 条（如 `creator-topic-library` 记录的竞态、排序口径不一致、临时文件残留）。
4. **重构前置条件成立**：某模块每次改动都要动 5 处以上才能保持一致——这说明抽象错了。
5. **性能或可维护性已阻塞新需求**：不重构就无法继续加功能。

### 不应重构

- 功能正在开发中途（先完成当前任务，避免基线与目标同时变动）。
- 没有可执行测试或验收手段（**无法验证行为等价，就不具备重构条件**）。
- 只是"看不顺眼"（风格问题交 lint / formatter，不交重构）。
- 交付节点前一晚（重构必须留出回归验证时间）。

## 输入

1. **代码地图**：本次要动的模块及其调用方（谁依赖它、它依赖谁）。没有调用方清单不得开工——否则改完不知道哪里会崩。
2. `docs/api-contracts.md`：作为**行为契约**，重构后必须逐项不变。
3. 现有测试：`.sdd/test-reports/**`、后端 `pytest` 用例、前端 typecheck / build、Playwright 用例（如有）。
4. `.sdd/experience.md`：该模块相关历史坑。
5. `.sdd/reviews/**`：Code Review 已报出的同类问题清单。
6. `docs/Plan.md`：该模块原定实现意图。

## 重构五步

### Step 1：界定目标与非目标

必须书面写出，落盘 `.sdd/refactor/plan-<module>.md`：

```markdown
# 重构方案：<模块名>

## 目标（做什么）
- 例：把 4 处重复的分页参数解析收敛到 `src/utils/pagination.py`

## 非目标（明确不做什么）
- 不改分页接口的请求/响应字段
- 不改默认每页条数
- 不调整前端分页组件的交互

## 行为等价性契约
以下外部行为在重构前后必须完全一致：
1. 接口 `GET /api/items?page=&size=` 的响应结构、字段名、类型、错误码
2. 越界页码的返回（空列表 vs 404）
3. size 超上限时的处理（截断 vs 报错）
4. 前端列表组件在 0 条 / 1 条 / 多页三种情况下的渲染

## 影响范围
- 修改文件：<清单>
- 调用方：<清单，必须完整>
- 不涉及：<明确排除的模块>

## 分批计划
- 第 1 批：<可独立验证的最小单元>
- 第 2 批：...
```

**「非目标」比「目标」更重要**：重构失控几乎总是因为范围蔓延，而不是因为技术方案错。

### Step 2：建立回归基线（无基线不开工）

这是本 Skill 的核心门槛。基线必须满足：

1. **可执行**：是一条能跑的命令，不是"我手动点一遍"。
2. **可对比**：重构前后跑同一条命令，结果可比。
3. **覆盖行为契约**：Step 1 列出的每条等价性契约都有对应用例。

基线形式按项目现状选择：

| 现状 | 基线做法 |
| ---- | -------- |
| 已有测试覆盖 | 直接跑现有测试，记录通过数与用例清单 |
| 覆盖不足 | **先补测试再重构**（补测试算重构的一部分，不算功能变更） |
| 纯前端无测试 | 固化 typecheck + build + 关键页面 Playwright 脚本 |
| 无法自动化 | 写出手动走查清单（参照 `sdd-release` 的 `manual-checklist.md` 格式），明确每步的预期观察结果 |

基线证据落盘：

```text
.sdd/refactor/baseline-<module>.md
```

内容：基线命令、执行结果（通过数 / 构建产物 hash / 截图路径）、测试用例清单。

> 若基线无法建立（如该模块完全没有可验证手段），**终止重构并告知用户**：先补可验证性，再谈结构。强行重构等于在没有护栏的路上换轮胎。

### Step 3：分批执行

每批必须满足：

1. **只动一个模块**：单批修改文件数量建议 ≤ 8，且同属一个逻辑单元。
2. **可独立验证**：每批结束立刻跑基线，必须全绿。
3. **可独立回滚**：每批一个独立 commit，commit message 标注 `refactor(<module>): <做了什么>`，body 中写「行为等价，基线 <路径> 全绿」。
4. **不与功能变更混批**：同一 commit 里出现新增字段、新页面、新接口 → 必须拆开。

执行方式按规模选择（判定标准见 `harness-core/skills/sdd-project-maintenance/SKILL.md`「小改 vs 大改」四维表）：

- 单模块内部调整、无接口变化 → 可直接执行，每批后跑基线。
- 跨前后端、涉及分层调整 → 按「大改」走 `Planner -> Developer -> Tester -> Code Review`，重构方案即 Delta Plan。

### Step 4：每批等价性验证

每批完成后必须给出证据：

```markdown
## 第 <n> 批验证

- 基线命令：<命令>
- 结果：<通过数> / 构建成功 / 类型检查通过
- 对比上一批：一致 / 差异说明
- 行为契约逐项核对：
  - [ ] 响应结构一致
  - [ ] 越界行为一致
  - [ ] 前端渲染一致
```

**"测试全绿"不等于行为等价**：测试只覆盖已写用例。必须额外做一次**契约逐项核对**——对着 `api-contracts.md` 一条条确认，尤其是测试未覆盖的边界（空数据、错误分支、极值）。

### Step 5：收口与经验回写

1. **Code Review 复核**：按 `harness-core/skills/sdd-code-review/SKILL.md` 审查，重点确认原有 `Major` 问题已消除、未引入新问题。
2. **更新 `.sdd/work-log.md`**：把已解决的技术债条目标记为已处理，附 commit 或批次号。
3. **经验回写**：按 `harness-core/protocols/development-rules.md`「经验沉淀链条」写入 `.sdd/experience.md`。重构产生的经验通常是"为什么原来的结构会错"这类根因型经验，价值高于单点避坑。
4. **清理基线文件**：`.sdd/refactor/` 保留方案与基线证据（作为后续同类重构的模板），不删除。

## 与其他角色的冲突处理

本 Skill 的入场不免除既有禁令，而是满足它们：

| 既有禁令 | 本 Skill 如何满足 |
| -------- | ----------------- |
| `sdd-bugfix`：禁止为了修 Bug 大范围重构 | 重构与 Bugfix **分两次做**：先修 Bug 让行为正确，再单独重构。若 Bug 根因是结构问题，Bugfix 只做最小修复 + 记录，重构另开批次 |
| `developer.md`：Edit with surgical precision | 每批改动都对应 Step 1 的「目标」条目与 Step 2 的基线用例，不存在"顺手改" |
| `maintenance`：Delta Plan 聚焦影响范围 | 重构方案即 Delta Plan，且额外要求「非目标」一节 |

冲突时的优先级：**行为正确性 > 行为等价性 > 结构美观**。三者冲突时，先放弃结构目标。

## 禁止

- 禁止在没有回归基线时开工
- 禁止在重构中修改 `docs/api-contracts.md` 定义的外部行为
- 禁止把重构与功能变更混在同一批或同一 commit
- 禁止"顺手"修 Bug 或加功能（发现即记录，另开流程）
- 禁止单批跨多个模块
- 禁止以"代码更好看"为由扩大范围
- 禁止用"测试全绿"替代契约逐项核对
- 禁止在交付节点前无缓冲时间时启动大范围重构
- 禁止重构未收口时进入 `sdd-release`（行为等价性未验证的版本不得发布）
